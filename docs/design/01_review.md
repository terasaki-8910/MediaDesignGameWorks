# 01 設計レビュー：要件整理・課題・方式比較・代替案

v0.1（[原本](00_original_v0.1.md)）を読み込み、要件を整理したうえで、実装前に決めておくべき論点を洗い出した。各論点の結論は [02_architecture.md](02_architecture.md)（技術設計）と [03_roadmap.md](03_roadmap.md)（計画）に反映している。調査日は 2026-10-27。

## 1. 要件整理

### 1.1 授業要件と、それを満たす仕組み

| ID | 授業要件 | 本設計での担い手 | 提出時に示す証拠 | 着手 |
|---|---|---|---|---|
| C1 | WebGL等によるブラウザゲーム | three.js（WebGLRenderer）によるゲーム本体 | 公開URLで開始からクリアまで遊べること | Phase 1 |
| C2 | Web上での公開 | Vercel。本番デプロイは GitHub Actions から実行 | 公開URLとデプロイ履歴 | Phase 0（骨組み） |
| C3 | プレイ結果・操作履歴の収集 | Telemetry System → `/api/telemetry`（Vercel Function）→ Supabase Postgres | 集計ビュー、ヒートマップ等の可視化 | Phase 0（骨組み）→ Phase 1 |
| C4 | LLMによる分析と改善 | AI Improvement Pipeline（Claude Code の非対話実行＋編集操作DSL） | 改善仮説・根拠・変更内容・検証結果の記録（`ai/history/`） | Phase 3 |
| C5 | Git管理と自動デプロイのループ | 定期ワークフロー（分析ジョブ → 適用・検証ジョブ → デプロイ） | コミット履歴、Actionsのログ、ゲーム内の改訂番号 | Phase 0（骨組み）→ Phase 4 |
| C6 | 紹介動画 | 決定的リプレイとオフライン描画キャプチャ（Playwright＋ffmpeg） | 動画ファイル | Phase 4 |

教員に肯定された構成（ログ保存、定期的なLLM実行、改善内容のpush、自動デプロイ）は、C3〜C5 の組み合わせでそのまま実現する。「ルールベースの動的難易度調整だけでは足りない」という点は、LLMが改善仮説を立て、変更の種類と値を選び、検証器を通った変更だけが反映される構造で満たす（§3.4）。

### 1.2 ゲーム要件と優先順位の扱い

v0.1 の優先順位（面白さと美しさ ＞ 特徴的な不可能建築の表現 ＞ LLMとの相性 ＞ 拡張性）は妥当なので、そのまま設計判断の基準にする。優先順位どうしが衝突したときの扱いを先に決めておく。たとえば「LLMに自由にステージを作らせたい（第三優先）」と「見た目と遊びの品質を守りたい（第一優先）」は衝突するので、本編ではLLMの変更範囲を、人間が品質を確認済みの選択肢（可変スロット）とパラメータに限定する。同様に「将来の重力反転（第四優先）」のためにVS段階で移動系を複雑にすることはせず、データモデルの拡張余地だけを残す。

### 1.3 本レビューで置いた前提（確認が必要）

開発体制はユーザー1名と Claude Code で、3Dアートも同じ体制で作ると仮定した。期間は承認後から約12週（2027年1月末）を仮定しており、manaba の正式な締切によってスコープを調整する。対象環境はデスクトップの Chrome / Edge / Firefox / Safari の最新版で、WebGL2 を必須とし、性能の基準機は統合GPUのノートPCとした。プレイヤー数は受講者・知人・SNS経由で延べ30〜100セッション程度、費用は各サービスの無料枠と月数十ドル以内のLLM利用料を想定した。UIは日本語と英語に対応する。これらは [README](README.md) の確認事項にまとめてある。

## 2. 技術的に難しい点・非現実的な点・曖昧な点

区分は「難所」（実現できるが設計しないと破綻する）、「非現実的」（記載どおりには成立しない）、「曖昧」（決まっていないと実装で迷う）の3種類。重要度は面白さ・提出要件・スケジュールへの影響で付けた。

| # | 区分 | 重要度 | 指摘 | 対応方針 |
|---|---|---|---|---|
| 1 | 難所 | 高 | 三人称の自由移動（ジャンプ・ダッシュ・落下）が「迷路を回避させない」制約とぶつかる。ジャンプや落下で想定外の近道が生まれ、検証器の論理グラフと実際の到達可能性がずれる | 「ポート封鎖規則」を導入する。歩行セルから出られるのは接続が一致したポートだけで、それ以外の境界は手すりと不可視ブロッカー（高さ3 m）で自動的に塞ぐ。ジャンプは操作感のための演出に限定し、論理には影響させない（§3.3） |
| 2 | 難所 | 高 | 変形中のプレイヤーの扱いが未定義。乗っている床が回る、回転体に押し出される、壁に埋まる、といった破綻が起こりうる | 「アンカー規則」：変形の操作は可動しないセルに置いたコンソールからのみ行う。変形中は入力をロックし、完了時に衝突体を確定する。検証器が回転の掃引領域とアンカーセルが交差しないことを保証する（§3.1, §3.3） |
| 3 | 難所 | 高 | 大型ブロックの回転では角が大きく掃引する。一辺 s の立方体を中心回転すると、角は面から (√2−1)s/2 の範囲を通過する（12 m立方体で2.49 m）。隣接する道路や橋に密着させると衝突する | 周囲に隙間を空け、ポートが一致した側だけ自動で伸びる渡し板でつなぐ。持ち上げて回す方法もあるが、一辺分以上持ち上げる必要があり時間がかかる。検証器が掃引干渉を判定する（数値は[検証結果](verification/README.md)） |
| 4 | 非現実的 | 高 | 自由に回せる三人称カメラでは、強制遠近法によるペンローズの階段はほぼ全ての角度で破綻する。Monument Valley で錯視が成立するのは、カメラが固定の正投影だから | 歩いて体験するループは「周期的な空間と見えないテレポート」で実現し、錯視の絵そのものは固定カメラの見せ場として分離する（§3.2） |
| 5 | 曖昧 | 高 | LLM改善ループ（Phase 3〜4）が計画の最後にあり、改善前後を比較できるだけのプレイデータが集まる期間がない。動画の必須要素である「改善前後の比較」が作れない恐れがある | 最初の週に、デプロイ・ログ・定期LLM・コミット・再デプロイを最小構成で一周させる（Walking Skeleton）。Area 1 のVertical Sliceを早期公開して、データ収集を前倒しする（[03](03_roadmap.md)） |
| 6 | 曖昧 | 高 | 締切、作業可能時間、3Dアートの担い手、プレイテスト参加者の見込みが書かれておらず、スコープを判断する前提がない | [README](README.md) の確認事項に挙げた。スコープを Must / Should / Could に階層化して、締切に合わせて切れるようにした |
| 7 | 難所 | 中 | 「変形は決められた条件を満たした場合にのみ実行できる」の条件が、恣意的なフラグになりやすい。プレイヤーには理不尽に見える | 条件は原則として物理的な干渉（掃引領域が他の建築とぶつかる）から自動的に導く。プレビューで干渉物を強調表示する。直感的で、検証器でも同じ計算ができる（§4.1） |
| 8 | 曖昧 | 中 | 7.1 の `nodes` / `connections` を手書きすると、見た目・衝突と論理グラフが食い違う。LLMに書かせると特に壊れやすい | 接続はポートの一致から計算で導く。手書きは非ユークリッド接続（周期リンクなど）に限定する（[02 §7.6](02_architecture.md)） |
| 9 | 非現実的 | 中 | LLMにステージJSON全体を生成・再生成させると、整合性も見た目の品質（配置の美しさ、装飾）も保てない | 本編は「編集操作DSL＋人間が用意した可変スロットの選択」とし、全面的な生成は別モード（Extra）に隔離する（§3.4） |
| 10 | 難所 | 中 | クリア率や時間だけを最適化すると、LLMはパズルを自明にする方向へ動く（グッドハートの法則）。改善のつもりで面白さが消える | セクションごとに人間が書く「意図契約」（教える内容、最短手数の帯、必須のギミック）を置き、検証器で強制する |
| 11 | 難所 | 中 | 数十セッション規模のデータでは統計的な判断が難しく、LLMがノイズに反応して変更を繰り返す | 新規セッション数によるゲート、Wilson信頼区間の併記、根拠が弱いときは低リスクな変更（ヒント時間・誘導）だけを許可、1回あたりの変更量の上限、同じ箇所の連続変更の禁止。ソルバー由来の静的指標も併用する |
| 12 | 難所 | 中 | Vercel Hobby は、コミットの作成者がプロジェクト所有者と一致しない場合にデプロイを止める。Bot によるコミットや、AIの共同作成者トレーラーで止まった報告もある | 本番デプロイは GitHub Actions から Vercel CLI で行い、本番ブランチの Git 連携デプロイは無効にする。Walking Skeleton で最初に検証する |
| 13 | 難所 | 中 | Supabase 無料プロジェクトは低活動が7日続くと一時停止する。2026-10-30 からは既存プロジェクトでも、public スキーマの新規テーブルが Data API に自動公開されず、明示的な GRANT が必要になる。API キーも旧 anon / service_role から publishable / secret への移行が進んでいる（二次情報では2026年末に旧キーを廃止予定） | 専用の `telemetry` スキーマと最小権限のDBロールを使い、マイグレーションに GRANT を明記する。日次の集計ジョブがDBを読むことで活動を維持する |
| 14 | 曖昧 | 中 | GitHub Actions の `schedule` は遅延することがあり、公開リポジトリで60日間活動がないと自動で無効化される | 手動起動（`workflow_dispatch`）を併用し、運用手順に再有効化を記載する |
| 15 | 非現実的 | 中 | Unity / Unreal の併用は、Three.js に移植できない資産を作る時間コストが大きい。紹介動画を Unreal で作ると「実際のゲームプレイ」と見た目が乖離する | 本線から外す。動画もゲーム本体の決定的リプレイから高画質でキャプチャする |
| 16 | 曖昧 | 中 | ミラーシフトが最終エリアで初登場し、同時に複合パズルにも使われる。5〜8分のゲームでは学習が間に合わない | Area 3 の冒頭に、ミラーシフト単独の学習ビートを置く |
| 17 | 曖昧 | 中 | 5〜8分に3エリアと大演出を詰める構成だが、エリアごとの時間配分と演出の長さが決まっていない | エリアごとの目標時間と演出の秒数を決める（§4.2、Area 1 は2.5〜3.5分） |
| 18 | 難所 | 低〜中 | Blender でのライトベイクと可動建築が矛盾する。動く建物に焼き込んだ影は一緒に動いてしまう | ベイクはモジュール単位のAOだけにし、直接光と影はリアルタイムで計算する |
| 19 | 難所 | 低 | ガラス・金属のリアルタイム平面反射は重い | 環境マップ（PMREM）とフレネルを基本にする。平面反射は見せ場1か所・半解像度に限定する |
| 20 | 曖昧 | 低 | `seed` の用途が不明（手作りのステージに乱数は要らない） | 背景都市と装飾の手続き生成にだけ使う |
| 21 | 曖昧 | 低 | 「粗く集計した移動経路」の粒度が未定義 | 2秒ごとに4 mセル単位へ量子化し、連続する重複を除いて送る |
| 22 | 曖昧 | 低 | 「難易度制約」の中身が未定義 | ソルバー指標（最短手数、状態数、初手の誤りによる追加手数）と、クリア率・中央値時間の目標帯を意図契約に書く |
| 23 | 曖昧 | 低 | 物理エンジンに何をさせるかが不明確 | Rapier はキャラクター移動、カメラ衝突、センサー（チェックポイント等）、CIでの通過テストに限定する。剛体シミュレーションは破片などの演出だけに使う |
| 24 | 曖昧 | 低 | 描画バックエンド（WebGL / WebGPU）が未決定 | WebGLRenderer を既定とし、Phase 0 のSpikeで WebGPURenderer と実測比較する（[02 §6](02_architecture.md)） |
| 25 | 曖昧 | 低 | プライバシーの告知と同意、学外公開時の扱い（研究倫理審査が要るかどうか） | タイトル画面での告知とオプトアウト、GPC / Do Not Track の尊重、IPアドレスを保存しない、保存期間の明示。審査の要否は授業担当に確認する |
| 26 | 曖昧 | 低 | 多言語対応とモバイルの扱い | UIは日本語・英語。モバイルでは非対応である旨を表示する |

特に影響が大きいのは 1〜5 である。1〜3 は「自由に歩けるのに、パズルとしては破綻しない」ための移動と変形のルールで、これが決まらないとステージ検証器も書けない。4 は不可能建築という作品の看板に関わる。5 は授業要件の達成そのものに関わる。

## 3. 実現方式の比較

### 3.1 建築変形

| 方式 | 概要 | 長所 | 短所 | 判定 |
|---|---|---|---|---|
| A. 剛体グループ変換＋運動学的な衝突体 | モジュール群を回転軸（ピボット）に束ね、時間関数で回す。衝突体は変形完了時に確定 | 決定的で検証できる。実装が単純 | 曲がる・伸びるといった非剛体の変形はできない | ゲームプレイに関わる全ての変形に採用 |
| B. GPU頂点アニメーション（インスタンス描画） | 背景のビル数千棟を頂点シェーダーで回転・折り畳み | CPU負荷がほぼゼロで、圧倒的な物量を出せる | 衝突がない。個別の細かい制御は粗い | 背景の大規模演出に採用 |
| C. Blenderで作るベイク済みアニメーション（glTFクリップ） | 折り紙のような多部品の展開を手付けする | 表現力が最も高い | データが重い。ステージ編集やLLMの変更に追従しない | 見せ場の一点物に限定 |
| D. 物理シミュレーション駆動（剛体と関節） | 動力学で倒す・組み上げる | 偶発的な迫力が出る | 非決定的で検証できない。挙動が不安定 | 不採用（破片の演出のみ可） |
| E. 空間歪みシェーダー（非剛体） | ビュー空間で曲げる・ねじる | ミラーディメンション的な歪みが出せる | 見た目と衝突が一致しない | 遷移の演出だけに使う |

ゲームプレイは A、背景は B、見せ場の一部だけ C、遷移の歪みに E、という組み合わせにする。v0.1 の 5.3 にある演出シーケンスは、A の変形に「エネルギー伝播（シェーダーの波）」「近接する装飾モジュールの遅延回転」「B による遠景の連鎖」「カメラパス」「音」を時間軸上で重ねたシーケンスとして実現する。シーケンスはステージデータから参照するので、LLMが配置を変えても演出は追従する。

変形の処理順は「論理が先、見た目が後」とする。コンソールで変形が確定した瞬間にパズル状態（論理）は目標状態へ移り、描画と衝突体はアニメーションで追いかける。アニメーション中は入力がロックされ、プレイヤーはアンカー（コンソールのセル）に固定されているので、動いている衝突体と干渉する心配はない。衝突体はアニメーション開始時に無効化し、完了時に最終姿勢で有効化する。

### 3.2 ペンローズの階段

| 方式 | 体験 | 自由カメラとの相性 | 実装コスト | 主なリスク | 判定 |
|---|---|---|---|---|---|
| A. 強制遠近法（特定の視点でだけ閉じて見える模型） | 見る | 悪い（その視点でしか成立しない） | 低 | 視点が外れると即座に破綻 | 見せ場の固定カメラでのみ採用 |
| B. 周期的な空間＋見えないテレポート | 歩いて永遠に登る | 良い | 低〜中 | 窓の外の景色、影、パーティクルの扱い | 採用（本命） |
| C. レンダーターゲットによるポータル | 離れた空間を覗く・通る | 良い | 中〜高 | 再帰描画の負荷、物理とカメラの受け渡し | 発展機能（Spatial Portal） |
| D. ステンシルによるポータル | 同一画面に別の空間を重ねる | 良い | 中〜高 | 透明物・ポストエフェクトとの干渉 | 発展機能 |
| E. 非ユークリッドレンダリング（レイマーチング等） | 本物の不可能空間 | 良い | 高 | 既存の描画パイプラインと両立しない | 不採用 |

B は数学的には「被覆空間」の考え方で、無限に続く螺旋階段を周期で割った空間を歩かせる。4本の階段が四角い吹き抜けを囲み、1本で1レベル（4 m）上がるので、一周すると16 m上にいる。周回の境目（継ぎ目）をプレイヤーが越えた瞬間に、プレイヤー・カメラ・カメラの追従状態・プレイヤーに付随するエフェクトをまとめて同じフレームで16 m下げる。階段の幾何を上下に数周期ぶん複製し、距離フォグで端を隠すので、吹き抜けを見上げても見下ろしても無限に続く階段が見え、継ぎ目は見えない。影を落とすライトの範囲はプレイヤーに追従させているので、移動の前後で影も一致する。窓の外の景色は、カメラの平行移動の影響を受けない遠景レイヤー（スカイボックスと同じ扱い）として描くので、16 mずれても気づかれない。

ペンローズの階段の「絵」（外から見ると閉じた四角形の階段が永遠に登っている図）は、歩くループとは別に作る錯視用の模型で見せる。Area 3 へ向かう途中に展望台を置き、そこではカメラを固定位置・固定画角に誘導する。模型は1つの角だけ奥行きが離れて作られていて、その視点からだけ閉じて見える。v0.1 の「見た目の建築形状と論理的な通路接続の分離」を、歩くループ（B）と見る模型（A）の分離として具体化した形である。

### 3.3 迷路の制約（移動と変形のルール）

自由に歩ける三人称視点と、検証できるパズルを両立させるために、次のルールを全ステージに適用する。

| ルール | 内容 | 狙い |
|---|---|---|
| R1 ポート封鎖 | 歩行セルの境界のうち、他のモジュールのポートと一致している面だけを通行可能にする。それ以外の境界には手すり（高さ1.1 m）と不可視ブロッカー（高さ3 m）を自動生成し、一致していないポートにはゲートを置く | ジャンプや落下による近道をなくし、論理グラフ＝実際の到達可能性にする |
| R2 アンカー | コンソールやミラー領域は可動しないセルに置く。変形中は入力をロックし、プレイヤーをアンカーに固定する | 変形中の押し出し・埋まり・落下をなくす |
| R3 掃引干渉 | 変形の掃引領域が他のモジュールと交差する遷移は実行できない。プレビューで干渉物を強調し、理由を表示する | 条件を物理的で直感的なものにし、検証器でも計算できるようにする |
| R4 有限状態と選択式の操作 | 各可動グループの状態は有限にする（姿勢を列挙する型は最大8状態、立方体の向きを扱う型は24通りの回転のうち到達できるものだけ）。コンソールでは Fold Mode に入り、許可された目標状態をプレビューしながら選んで確定する | 操作ミスを減らし、試行錯誤のコストを「歩いてコンソールへ行くこと」に集中させる |
| R5 詰み防止 | 検証器は、到達可能な全状態からゴールに到達できること（詰み状態0）を保証する。実行時にもソルバーで詰みを検出し、リセットを促す | 進行不能を構造的に防ぐ |
| R6 ジャンプは演出 | ジャンプの最大高さは1.0 m。R1 によりジャンプで到達できる場所は論理的に増えない | 操作感を保ちながらパズルの成立性を守る |

移動の制約を実現する方式として、物理任せ（ジャンプと落下を自由にする）、ポート封鎖（R1）、ノード移動（Monument Valley 型のクリック移動）の3案を比較した。物理任せは自由度が高い代わりに近道が生まれて検証が難しく、ノード移動は完全に制御できる代わりに三人称視点の没入感が失われて v0.1 の仕様とも合わない。ポート封鎖は手すりが増えることだけが欠点で、これはエッシャーの建築に通じる意匠（欄干、胸壁、アーチ）としてデザインで吸収できる。したがって R1 を採用する。なお、意図的に一方通行の落下を使いたい場所には「ドロップポート」を明示的に置けるようにする。

### 3.4 LLMによる生成・改善

| 方式 | LLMの出力 | 品質の維持 | 検証のしやすさ | 生成の度合い | 判定 |
|---|---|---|---|---|---|
| A. ステージJSON全体の再生成 | 全文 | 悪い | 悪い | 高 | 不採用 |
| B. JSON Patch（RFC 6902） | 差分 | 中（意味を知らない編集が起きる） | 中 | 中 | 不採用 |
| C. 編集操作DSL＋可変スロット | 操作の列（スロットの選択、パラメータの変更） | 良い | 良い | 低〜中 | 本編に採用 |
| D. パラメータ調整のみ | 数値 | 良い | 良い | 低 | 採用（Tier 0） |
| E. 生成と検証の反復（LLM＋ソルバー） | 新規の小部屋 | 中（キットの質に依存） | 中 | 高 | Extraモードに採用（Tier 2） |
| F. ソースコードの変更 | パッチ | 不明 | テスト次第 | — | PRと人間の承認に限定（Tier 3） |

変更の権限は段階（Tier）で管理する。Tier 0 は範囲が決まったパラメータ（ヒントが出るまでの秒数、誘導光の強さ、カメラヒントの角度、移動速度など）で、自動適用する。Tier 1 は人間が用意した可変スロットの選択肢（コンソールの設置位置の候補、チェックポイントの位置、看板や誘導の配置など）で、これも自動適用する。スロットの選択肢は開発時に人間と Claude Code が見た目を整え、検証も済ませておくので、LLMが選んでも品質は落ちない。Tier 2 はLLMが新しいレイアウトそのものを生成するもので、本編には自動適用せず、Extra モード（「アーカイブ」と呼ぶ小部屋集）に公開する。Tier 3 はコードの変更で、PRを作るところまでに留め、人間が承認する。

Tier 2 は「生成」の要件を正面から満たす部分である。LLMがキットの部品で小部屋を組み、コンパイラとソルバーが最短手数・状態数・詰みの有無を計算して返し、LLMがそれを見て修正する、という反復をエージェントのループで回す。検証を通った部屋だけがアーカイブに追加され、プレイデータの評価が低い部屋は引退する。本編の品質を守りながら、AIが自分で作り、自分で選別するループを見せられる。

### 3.5 LLMの実行方式

| 方式 | 内容 | 長所 | 短所 | 判定 |
|---|---|---|---|---|
| A. `anthropics/claude-code-action` | GitHub公式のActionに prompt を渡して実行 | Actionsとの統合が簡単で、定期実行の公式例もある | 自動モードでのコミットとプッシュの挙動が文書化されておらず、プッシュを止める入力もない | 次点 |
| B. Claude Code CLI の非対話実行（`claude -p`） | ワークフローのステップで直接実行 | 許可するツール、ターン数、出力形式を細かく指定できる | ログの整形は自前 | 推奨 |
| C. Claude Agent SDK（TypeScript） | スクリプトから呼び出す | フックやコールバックで最も細かく制御できる | 実装量が増える | 代替 |
| D. Messages API の単発呼び出し＋構造化出力 | 1回のリクエストで提案JSONを得る | 最も安く、最も決定的 | エージェントが自分で検証して直すループがない | フォールバック |
| E. Managed Agents（Anthropic側でホスト） | スケジュール実行も含めて委託 | インフラが要らない | リポジトリやDBとの連携を別途設計する必要がある | 不採用 |

授業のテーマが「CLIエージェントの活用、ハーネスおよびループエンジニアリング」なので、B を本命にする。エージェントには読み取りと、提案ファイル1つへの書き込みと、検証コマンド1つの実行だけを許し、デプロイの権限は渡さない。エージェントが書いた提案は、別ジョブが決定的なコードで適用し、検証し、合格したときだけコミットとデプロイを行う。エージェント自身の「検証しました」という報告は信用せず、外側のハーネスが必ず検証し直す。詳細は [02 §7.9](02_architecture.md)。

### 4.2 エリア別の具体案

**Area 1：The Fold（Vertical Slice の範囲、目標2.5〜3.5分）** は3つのセクションと終盤の演出で構成する。1-2 と 1-3 は、状態探索で解けること、最短手数、詰み状態がないことを確認した（[検証結果](verification/README.md)）。1-1 は1手で終わる導入である。

1-1「最初の折り目」は、屋上の遊歩道の先で道が途切れている場所から始まる。手前のコンソールで道路ブロックを90度回すと道がつながる。最短1手で、コンソール、プレビュー、接続の光を教える。

1-2「パスキューブ」では、巨大な立方体の上面が交差点になっている。最初は上面の道が南北に走っているので、西から来たプレイヤーは東へ渡れない。西の道路には「転がす」コンソールがあり、北のバルコニーには「回す」コンソールがある。正解は、西で立方体を転がして北面の道（西と北をつなぐ角の道）を上に向け、北のバルコニーへ渡り、そこで立方体を回して道を北と東をつなぐ向きに変え、東へ抜けるという2手である。西のコンソールだけで試せる4通りの状態のどれにも西と東を直接つなぐ道はないので、総当たりでは抜けられず、北のバルコニーへ行くこと自体が発見になる。誤った初手（180度・270度の転がし）は1手の遠回りで済み、詰みは起きない。なお、コンソールが「90度ずつ」しか回せない設計だと最短手数が4手に増えることも確認したので、Fold Mode では目標状態を選べるようにする。

1-3「フォールド・ゲート」では、谷の手前に、ビルが壁から横向きに生えた状態で垂直に立つ街路（折り畳まれた街区）がある。これを倒すと谷を渡る橋になり、横向きだったビルが起き上がって、両側にビルが並ぶ通りになる。これが Area 1 最大の見せ場である。ただし谷の中に立つ塔のアームが、街路を倒すときの掃引領域に入っている。アームが手前の広場と横の岩棚をつなぐ状態でも、やはり掃引領域に入る。街路を倒すコンソールは岩棚にしかない。正解は、広場で塔を回して岩棚へ渡り、岩棚でもう一度塔を回してアームをどかし（このとき自分は岩棚に取り残される）、街路を倒して、倒れた街路を渡るという3手である。「自分の退路を断つ」ことを受け入れる瞬間が、このセクションのひらめきになる。誤った初手は1手の遠回りで、詰みはない。街路が倒れると遠景の都市が連鎖的に折り畳まれ（GPUの背景演出）、谷が閉じてコアへの門が開く。

**Area 2：The Spiral（目標2〜2.5分）** は、コアの塔を取り巻くアルキメデスの螺旋の回廊を登るエリアである。回廊の中心線は r = r_out − bθ、高さは h = cθ（高さは回転角に比例）とする。腕と腕の半径方向の間隔は 2πb、1周あたりの上昇量は 2πc になる。この螺旋を Δθ だけ回転させると、固定された方向から見た半径は bΔθ、高さは cΔθ だけずれる（1周回すと元の形に重なる）。この性質を使い、外壁や塔に固定された踊り場が、螺旋の回転状態（90度単位の4状態）ごとに別々の腕と接続するようにする。どの回転状態でどの踊り場とどの踊り場が同じ腕でつながるかを読み解くのがパズルになる。推奨パラメータは r_out = 28 m、r_in = 12 m、通路幅4 m、腕の隙間6 m（b ≒ 1.59 m/rad）、1周の上昇8 mで、約1.6周、延長約200 m、総上昇12.8 m、最大勾配10.5%（約6度）、最小曲率半径11.9 mとなり、歩行とカメラの両面で無理がない。90度回したときのずれは半径方向2.5 m・高さ2.0 mで、ジャンプで届いてしまう距離なので、R1 に従い、一致していない踊り場はゲートで閉じる。具体的な配置は Phase 2 でソルバーを使って設計する。

**Area 3：The Impossible Stairway（目標2〜2.5分）** は、冒頭でミラーシフトを単独で学ぶ部屋（A層では行き止まりの階段、B層では橋）から始まる。続く本題では、ペンローズの階段のループがゼンマイになっている。周回数（0〜3の4値）が外の時計塔の針と橋の向きを決め、出口の扉はB層にしかない。プレイヤーは、周回して針を合わせ、ループ上の鏡の床でB層へ切り替え、扉から橋へ出る。状態探索では、周回数・位置・層の組み合わせが37状態、最短の能力使用は1回（ミラーシフト）で、周回数が合えば解けることを確認した。目標の周回数を2にすると、上りで2周しても下りで2周しても同じになり、「登るほど進む」という手応えが薄れることも分かった。そこで最初の目標は1（または3）にし、目標の周回数をLLMが調整できる難易度パラメータにする。

### 4.3 削る・後回しにする提案

Unity と Unreal は本線から外す。完全な非ユークリッド空間（ポータル）は発展機能に回し、初期版のペンローズ体験は周期空間（§3.2 の B）で実現する。自由なジャンプによる探索は演出に限定する（R6）。「都市全体の万華鏡的な増殖」は背景のGPU演出とポストエフェクトで実現し、ゲームプレイには入れない。ソースコードの自動改変は Tier 3（PRと人間の承認）に限定する。Gravity Shift などの将来の能力は完成版の範囲外とし、データモデルに拡張の余地だけを残しておく（状態の種類、リンクの種類、条件式を後から追加できる形にしている）。
